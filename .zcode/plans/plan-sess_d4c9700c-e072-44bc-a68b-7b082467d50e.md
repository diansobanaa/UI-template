# Plan: Make AgroTech UI Fully Functional (CRUD, Validation, Mock Lifecycle)

Codebase: Next.js 15 App Router + React 19 + Tailwind v4, pages → `src/lib/services.ts` → `src/lib/store.ts` (mock DB) → `src/lib/data/*`. Architecture is already backend-ready (spec #2/#39 satisfied). Work focuses on closing functional gaps **without changing the approved design** (spec #45) and respecting the Vite migration constraints (only `next/link`, `router.push/replace`, `useSearchParams`; all pages stay `"use client"`).

## 1. Foundation — persistence & shared infra (Priority 3 groundwork)

- **`src/lib/store.ts`**: add localStorage persistence — load `MockDb` from `localStorage["agrotech-db-v1"]` on first access (fall back to seed data), save on every mutation via a single `persist()` helper. Add `resetMockDb()` (restores seed data) + a "Reset Demo Data" entry point (header overflow or settings-less location such as the sidebar footer, minimal visual footprint).
- **`src/lib/validation.ts`** (new): tiny framework-free helpers — `required`, `number` (min/max/positive), `time`, `date`, `duplicateId`, plus a `FieldErrors` record type and `<FieldError>` display component wired into the existing `Label`/`Input` primitives (red text under field, spec #20 — errors appear near the field).
- **Standardize service errors** (spec #21): add `ServiceError { code, message }` thrown by services (e.g. `VALIDATION_FAILED`, `DUPLICATE_ID`, `NOT_CONNECTED`); `src/lib/api/backend-client.ts` gains a `parseError` path so future REST errors map to the same shape.
- **Mutation helper** `withMutation(fn, {loadingKey, toast})` used by pages: sets button pending state, disables submit while pending (spec #24/#25), toasts success/error, and returns a discriminated result so callers can roll back.

## 2. Edit mode for all three schedule drawers (Priority 1–2)

Convert `AddFertigationDrawer.tsx`, `AddWellPumpDrawer.tsx`, `AddFanScheduleDrawer.tsx` to accept `initial?: FertigationSchedule | WellPumpSchedule | FanSchedule` and a `mode: "create" | "edit"`:

- Drawer title/submit label switch (Edit Schedule / Save Changes), form pre-filled from `initial`.
- Add `scheduleService.update*` functions in `src/lib/services.ts` + `updateSchedule*` in `store.ts` (replace in GH's nested arrays by id; well pump at complex level).
- **Validation** on submit for every form: required name, numeric/positive durations/volumes, valid time/date, interval sanity, temperature hysteresis rule (ON threshold > OFF threshold), duplicate schedule name within the same GH (spec #20).
- Submit flow: validate → service call → success: update list/timeline/next-schedule card, close drawer, toast; failure: keep drawer open, show error, no local change (spec #8/#9/#13).
- Wire `onEdit` in `schedule/page.tsx` to open the same drawer in edit mode (replacing the current placeholder toast at lines ~180/218/284).

## 3. Delete/disable hardening (spec #14/#36)

- Keep existing ConfirmDialog flows; ensure optimistic delete with rollback: remove row immediately with "Deleting…" state; on service failure re-insert at original index + error toast. Disable stays a simple toggle (already works) with pending state.
- Add delete confirmations where missing across pages (complex/GH deletes are out of UI scope today; schedule-level only, per available UI).

## 4. Mock lifecycle for physical/system actions (spec #16/#23/#33/#37/#38)

Implement through services — no `setTimeout` success in components:

- **`fertigationService.startManual`**: creates a real `CurrentFertigation` run in the GH store (steps derived from selected recipe/tank), transitions over a few simulated ticks (requested → running → completed) via a small `mockClock` in the service; fertigation page shows the run's actual state; on simulated failure (deterministic, e.g. device offline flag) state returns to idle + error toast.
- **`syncEsp32`**: per-target (complex or GH) — sets config state to `Syncing…`, then `Synced`, bumps ESP32 version only on success (spec #34); failure leaves previous version/state (spec #26). Wire the Sync buttons on dashboard, schedule page, and fertigation page to it.
- **`emergencyStop`**: sets GH/complex running state to stopped + shows a confirmation dialog first ("This affects physical equipment") and displays command status (Requested/Accepted/Failed) per spec #37.
- **Pump Test Run / Calibrate** on fertigation page: service calls that log an event and set a transient running state on the equipment item; no silent success.
- **Well pump radar rule** (spec #16): already modeled as `radar: "filling" | "full"`; add UI representation on the dashboard/complex well pump card — schedule stays enabled, pump shows "Pump OFF — tank full (radar)" when full, never a percentage.
