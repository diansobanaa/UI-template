# CANONICAL SPECIFICATION: RAW WATER FLOW SENSOR (ZJ-B1) VERIFICATION & PHYSICAL CALIBRATION

## 1. Overview & Scope
This document specifies the authoritative operational model, API contracts, telemetry format, mathematical formulas, and staged physical verification protocol for the **12V DC Raw Water Submersible Pump** and **ZJ-B1 DN15 Hall-Effect Flow Sensor** in the AgroTech Greenhouse Controller.

## 3. Mathematical Formulas

### 3.1. Candidate Flow Sensor Calibration Factor ($K_{\text{candidate}}$)
The pulse-per-liter calibration factor represents the number of pulses generated by the Hall-effect turbine per liter of water transferred:

$$K_{\text{candidate}} = \frac{N_{\text{session pulses}}}{V_{\text{actual in liters}}} \quad [\text{pulses/L}]$$

*Note: If the physical measurement is taken in milliliters ($V_{\text{actual, ml}}$), it is converted to liters ($V_{\text{actual, L}} = V_{\text{actual, ml}} / 1000$) prior to calculating $K$.*

### 3.2. Actual Raw Water Pump Flow Rate ($Q_{\text{actual}}$)
The physical pump flow rate is calculated independently from the sensor factor:

$$Q_{\text{actual, ml/s}} = \frac{V_{\text{actual, ml}}}{t_{\text{session, s}}} \quad [\text{mL/s}]$$

$$Q_{\text{actual, L/min}} = \frac{Q_{\text{actual, ml/s}} \times 60}{1000} \quad [\text{L/min}]$$

*Critical Rule:* Pump delivery rate ($Q$) and flow sensor pulses-per-liter factor ($K$) are strictly separate parameters and persisted to distinct configuration registers.

### 3.3. Estimated Flow Volume from Sensor Pulses ($V_{\text{estimated}}$)
When a valid calibration factor ($K > 0$) is available:

$$V_{\text{estimated, L}} = \frac{N_{\text{session pulses}}}{K} \quad [\text{Liters}]$$

$$V_{\text{estimated, ml}} = V_{\text{estimated, L}} \times 1000 \quad [\text{mL}]$$

*Mandatory Rule:* When no valid calibration factor exists ($K \le 0$ or status is `UNCAL`), the estimated volume is **NEVER** fabricated or displayed as accurate liters. The UI displays "Belum Dikalibrasi (Estimasi Tidak Tersedia)" while continuing to display raw pulse counts and pulse frequency.

### 3.4. Verification Percentage Error ($E_{\%}$)
The relative error between estimated volume and physically collected volume:

$$E_{\%} = \frac{|V_{\text{estimated}} - V_{\text{actual}}|}{V_{\text{actual}}} \times 100\%$$

### 3.5. Acceptance Tolerance
- **Proposed Acceptance Tolerance:** $\pm 5.0\%$.
- A validation run is accepted (`isPassed: true`) only when $E_{\%} \le 5.0\%$.

## 4. Staged 3-Run Verification Protocol

To prevent single-run anomalies from corrupting production fertigation mixing recipes, the workflow enforces a staged protocol:

```
[Start Session]
       │
       ▼
[Run 1: Initial Calibration] ──► Measure Physical Vol ──► Calculate K_candidate ──► Status: CALIBRATION_PENDING
       │
       ▼
[Run 2: Validation Run 1]    ──► Measure Physical Vol ──► Compare Est vs Act    ──► Verify Error <= 5.0%
       │
       ▼
[Run 3: Validation Run 2]    ──► Measure Physical Vol ──► Compare Est vs Act    ──► Verify Error <= 5.0%
       │
       ▼
[Both Validations Pass?]
  ├── YES ──► Promote to VERIFIED ──► Persist to NVS (flowRawPulsesPerL, state: VERIFIED)
  └── NO  ──► Status remains CALIBRATION_PENDING / FAILED (Preserve existing calibration)
```

1. **Run 1 (Initial Calibration):**
   - Collect physical water in container.
   - Enter measured volume in liters.
   - Calculate candidate pulses-per-liter factor ($K_{\text{candidate}}$).
   - Sensor state is marked `CALIBRATION_PENDING` (never automatically `VERIFIED`).
2. **Run 2 (Independent Validation 1):**
   - Start fresh test session with fresh pulse baseline.
   - Calculate live estimated volume using $K_{\text{candidate}}$.
   - Collect and measure physical volume independently.
   - Compute percentage error $E_{\%}$. Must satisfy $E_{\%} \le 5.0\%$.
3. **Run 3 (Independent Validation 2):**
   - Repeat independent measurement.
   - Compute percentage error $E_{\%}$. Must satisfy $E_{\%} \le 5.0\%$.
4. **Promotion to `VERIFIED`:**
   - The sensor factor is promoted to `VERIFIED` only after both validation runs satisfy the $\pm 5.0\%$ tolerance.
   - If any validation run fails, the candidate is flagged and existing production calibration is preserved.

## 6. Safety Interlocks & Hardware Guardrails
1. **Dosing & Mixing Isolation:** While `pump_submersible` calibration is active, GPIO 5 (Dosing A), GPIO 6 (Dosing B), and GPIO 40 (Mixing Pump) are locked idle.
2. **Authoritative Runtime Limit:** Hard firmware ceiling of 1800 seconds (30 minutes) maximum runtime.
3. **Non-Resetting Pulse Counter:** Lifetime hardware counter is never reset; sessions calculate pulses strictly as $\Delta N = \text{current} - \text{start}$.
4. **Session Freeze:** Upon completion or operator stop, telemetry counters are frozen immediately to prevent post-test piping coasting pulses from distorting calculations.
5. **Safe Stop:** Upon browser disconnect, timeout, or emergency stop, GPIO 4 is de-energized immediately.

## 7. Real-Time Telemetry Streaming & Freshness Architecture

### 7.1. Direct Hardware ISR Sampling
- Direct pulse reading is provided via `sensor_hal_get_raw_flow_pulses()`, reading the atomic 32-bit `s_pulses_raw_zjb1` accumulated by GPIO 15 ISR (`GPIO_INTR_NEGEDGE`).
- Calibration worker and `calibration_mgr_get_status()` sample this direct hardware counter without waiting for the 2000ms global sensor sampler task.
- Arithmetic handles 32-bit unsigned rollover safely:
  $$\Delta N = \begin{cases} N_{\text{current}} - N_{\text{start}}, & \text{if } N_{\text{current}} \ge N_{\text{start}} \\ (2^{32} - N_{\text{start}}) + N_{\text{current}}, & \text{if } N_{\text{current}} < N_{\text{start}} \end{cases}$$

### 7.2. Client-Side Bounded Poller & Sequence Tracking
- Polling runs at ~1Hz during active testing using a recursive bounded sequence (`setTimeout` with `AbortController` and 2000ms timeout).
- Overlapping requests are prevented because the next polling cycle is scheduled only after the prior request completes.
- Monotonic sequence numbering (`pollSeqRef` / `latestHandledSeqRef`) drops any slow, delayed, or out-of-order network responses.

### 7.3. Telemetry Freshness Classifications
- **`LIVE` (Green):** Telemetry received within 2.5 seconds (`age <= 2500ms`).
- **`STALE` (Amber):** Telemetry delayed between 2.5 and 6.0 seconds (`2500ms < age <= 6000ms`).
- **`DISCONNECTED` / `ERROR` (Red):** Communication failed or no response for > 6.0 seconds (`age > 6000ms`).
- Telemetry age is explicitly exposed in the UI header. Data is never simulated or fabricated.
